# Архитектурные решения (ADR)

Формат: контекст → решение → последствия. Каждое решение принято самостоятельно
там, где задание оставляет неоднозначность.

## ADR-001. Объём: только backend, без фронтенда

**Контекст.** Задание описывает интеграционный сервис с REST API; UI не требуется.
**Решение.** Фронтенда нет. Интерфейс для человека - Swagger UI (`/docs`).
Понятий «пользователь/регистрация» и сущностей Run/NodeRun в предметной области
нет; вместо них в ARCHITECTURE.md описаны автоматы обработки сообщения и
жизненного цикла консьюмера.

## ADR-002. Драйвер MongoDB: асинхронный API PyMongo

**Решение.** `pymongo.AsyncMongoClient` (PyMongo ≥ 4.10), а не Motor.
**Почему.** Motor объявлен устаревшим в пользу нативного async API PyMongo;
нативный клиент не гоняет вызовы через пул потоков.

## ADR-003. Клиент RabbitMQ: aio-pika

**Решение.** `aio-pika` и в приложении, и в продюсере.
**Почему.** Нативный asyncio, работает в одном event loop с FastAPI, поддерживает
publisher confirms и `mandatory`.

## ADR-004. Консьюмер в lifespan FastAPI, последовательная обработка

**Решение.** Консьюмер - фоновая `asyncio.Task`, запускаемая в `lifespan`.
Сообщения обрабатываются по одному (`prefetch_count=10` как буфер).
**Почему.** Выполняет требование «консьюмер внутри приложения», не требует
отдельного процесса. Последовательная обработка проще для рассуждений;
пропускной способности одной очереди и одной реплики для задачи достаточно,
масштабирование - репликами (корректность обеспечена идемпотентностью, ADR-007).

## ADR-005. Топология: direct exchange + quorum queue + DLX

**Решение.** Exchange `calls` → quorum queue `calls.results`
(`x-delivery-limit=5`, `x-dead-letter-exchange=calls.dlx`) → DLQ `calls.results.dead`.
**Почему.** Невалидные сообщения не теряются молча и не крутятся в очереди
бесконечно; quorum queue считает доставки, что даёт защиту от «ядовитых»
сообщений при временных сбоях. Публикация в именованный exchange, а не в
default exchange, позволяет позже добавить других подписчиков без изменения
продюсера.
**Последствия.** Продюсер и консьюмер обязаны объявлять очередь с одинаковыми
аргументами - это проверяет тест `test_producer_topology_matches_app`.

## ADR-006. Семантика подтверждений и повторов

- невалидное сообщение или конфликт данных → `reject(requeue=False)` → DLQ;
  лог `WARNING`/`ERROR`;
- MongoDB временно недоступна → повтор **на месте** с экспоненциальной паузой
  (`retry_delay_seconds` → … → `storage_retry_max_delay_seconds`), сообщение не
  подтверждается и не возвращается в очередь;
- непредвиденное исключение → пауза `retry_delay_seconds` → `nack(requeue=True)`;
  после `x-delivery-limit` доставок RabbitMQ переносит сообщение в DLQ;
- успех или точный дубликат → `ack`.

**Почему.** Требования «ack только после успешной записи в БД» и «некорректные
сообщения не роняют консьюмер». Первая версия возвращала в очередь при любой
ошибке БД - интеграционный тест показал, что при простое MongoDB дольше
`delivery-limit × пауза` (≈ 6 с) исправные сообщения уходили в DLQ. Поэтому
временные ошибки хранилища отделены от «ядовитых» сообщений: первые ждут
восстановления БД, вторые ограничены счётчиком доставок.
**Последствия.** Пока MongoDB недоступна, консьюмер стоит на одном сообщении -
это сознательный back-pressure: остальные сообщения всё равно не удалось бы
записать.

## ADR-007. Идемпотентность вместо транзакций

**Решение.** Уникальные индексы по `campaign_id` и `call_id`; кампания -
upsert с `$setOnInsert`; звонок - `insert_one` с обработкой `DuplicateKeyError`.
Дубликат с теми же данными подтверждается, с другими - отклоняется в DLQ как
конфликт. Транзакции не используются.
**Почему.** RabbitMQ даёт at-least-once, повторы неизбежны. Транзакции требуют
replica set и не нужны: кампания создаётся идемпотентно до звонка.
**Последствие.** Повторный запуск `producer.py` не создаёт дублей - в ответе API
для `camp_001` остаётся ровно 2 звонка.

## ADR-008. Формат сообщения: плоский JSON с данными кампании

**Контекст.** Кампания создаётся из сообщения о звонке, а у неё обязательные
`name` и `created_at`, которых нет в модели звонка.
**Решение.** Обязательны только пять полей звонка из задания (`call_id`,
`campaign_id`, `phone`, `status`, `created_at`). Сообщение может дополнительно
нести `campaign_name` и `campaign_created_at`. Без `campaign_name` кампания
получает название, равное `campaign_id`; без `campaign_created_at` она получает
`created_at` первого пришедшего звонка. Первое сообщение задаёт поля кампании;
другое имя в последующих сообщениях логируется (`WARNING`) и не перезаписывает
данные, а отсутствие имени конфликтом не считается.
**Пересмотрено после ревью.** Сначала `campaign_name` был обязательным, и
сообщение ровно в формате звонка из задания уходило в DLQ. Наш продюсер имя
отправляет, поэтому сценарий проверки проходил, но сообщения проверяющего по
формату из задания не сохранились бы.
**Почему.** Сообщение самодостаточно, сервис не зависит от внешнего справочника
кампаний. Брать текущее время сервера для `created_at` кампании хуже: при
повторной обработке очереди даты «поплывут».

## ADR-009. Валидация полей

- `call_id`, `campaign_id`: `^[A-Za-z0-9][A-Za-z0-9_.:-]{0,63}$`;
- `phone`: только цифры, 10-15 знаков (E.164 без `+`), первая не `0`, как в
  примере из задания (`79001234567`). `+7 900 123-45-67` отклоняется: сервис не
  нормализует номера, это зона продюсера;
- `status`: `^[a-z][a-z0-9_]{0,31}$` - не жёсткий enum. Набор статусов телефонии
  у разных провайдеров разный; отбрасывать в DLQ звонок из-за нового статуса
  хуже, чем сохранить его. Формат при этом ограничен;
- даты: обязательно с часовым поясом (naive datetime отклоняется), хранятся в UTC;
- `campaign_name` (необязательно): 1-200 символов после обрезки пробелов;
- неизвестные поля игнорируются.

## ADR-010. Ответ «Кампания не найдена»

**Контекст.** Задание требует `200` с текстом «Кампания не найдена» и схему
ответа в Pydantic.
**Решение.** `200` и JSON `{"detail": "Кампания не найдена"}` (модель
`CampaignNotFoundResponse`). `response_model` эндпоинта -
`CampaignCallsResponse | CampaignNotFoundResponse`, оба варианта видны в Swagger.
**Почему.** Один `Content-Type` (JSON) для всех ответов эндпоинта, клиенту не
нужно разбирать `text/plain` отдельно, и обе ветки описаны схемой.
Кампания «существует», если есть документ в `campaigns`.
`campaign_id` в пути проверяется только по длине (1-256 символов), а не шаблоном
идентификатора: кампании с идентификатором вне шаблона не существует (сообщения
проходят тот же шаблон), и на неё тоже отвечаем 200 «Кампания не найдена», а не 422.

## ADR-011. Ответ со списком - объект-обёртка с пагинацией

**Решение.** `{"campaign_id", "total", "limit", "offset", "calls": [...]}`,
`limit` по умолчанию 100 (максимум 1000), `offset` от 0 до 1 000 000, сортировка
`created_at, call_id`. Верхняя граница `offset` нужна потому, что `$skip` в MongoDB
принимает только int64: без неё огромное значение давало 500, теперь 422.
**Почему.** Голый массив нельзя расширить без поломки клиентов; неограниченная
выборка - риск для больших кампаний.

## ADR-012. Продюсер самодостаточен

**Решение.** `producer.py` не импортирует пакет `app`, зависит только от
`aio-pika` (`requirements-producer.txt`). По умолчанию подключается к
`amqp://guest:guest@localhost:5672/` (порт проброшен из compose), адрес
меняется переменной `RABBITMQ_URL`. Публикует 4 детерминированных сообщения
(`call_0001`…`call_0004`, кампании `camp_001`, `camp_002`) с publisher confirms
и `mandatory=True`, `delivery_mode=persistent`.
**Почему.** Сценарий проверки - `python producer.py` с хоста: зависимостей
должно быть минимум. Детерминированные идентификаторы делают повторный запуск
безопасным. Альтернатива без установки пакетов - `docker compose run --rm producer`.

## ADR-013. Health как readiness

**Решение.** `/health` отвечает `503`, пока MongoDB не пингуется или консьюмер не
в состоянии `consuming`. Healthcheck контейнера смотрит туда же.
**Почему.** `healthy` в `docker compose ps` должен означать «можно запускать
продюсер».

## ADR-014. Инструменты качества

`ruff` (lint + format), `mypy --strict`, `pytest` + `pytest-asyncio`.
Юнит-тесты не требуют внешних сервисов (in-memory реализация репозитория как
тестовый двойник). Интеграционные тесты идут против реальных MongoDB и
RabbitMQ; если сервисы недоступны, они **пропускаются с явной причиной**, а не
подменяются моками.

## ADR-015. Версии образов

`mongo:7.0`, `rabbitmq:4.1-management-alpine`, `python:3.12-slim`. Версии
закреплены по minor, чтобы `docker compose up` был воспроизводим.
Приложение совместимо с Python 3.10+ (требование задания), образ - 3.12.

**Почему MongoDB 7.0, а не 8.x.** Первая версия использовала `mongo:8.0`, и
первый же прогон CI упал: MongoDB 8.0 и 8.3 намеренно отказываются стартовать
на ядре Linux 6.19 и новее ("Linux kernel versions 6.19 and newer has a known
incompatibility"), а раннеры GitHub уже на ядре 7.0. Та же проблема была бы у
проверяющего на свежем Linux-хосте. `mongo:7.0` стартует на всех проверенных
ядрах; сервис не использует возможностей 8.x (нужны уникальные индексы, upsert,
`$facet`), поэтому откат версии ничего не стоит. Когда исправление в 8.x станет
надёжным (SERVER-125742, SERVER-136848), версию можно поднять.

## ADR-016. Кроссплатформенность: Linux и Windows как равноправные хосты

**Контекст.** Задание не задаёт ОС. Сервис работает в Linux-контейнерах, но
`python producer.py` проверяющий запускает на своей машине - это может быть
Windows. Первый запуск в PyCharm на Windows упал: `requirements.txt` был
зафиксирован под Linux и тянул `uvloop`, который под Windows не собирается.
**Решение.**
- `requirements.txt` - универсальный lock (`uv pip compile --universal`):
  платформенные зависимости помечены маркерами окружения;
- одинаковые задачи для двух оболочек: `Makefile` (bash) и `tasks.ps1`
  (Windows PowerShell 5.1 и PowerShell 7, только ASCII, CRLF);
- логика, которая не должна расходиться, написана один раз на Python:
  `scripts/smoke_check.py` (сценарий проверяющего), сами скрипты-обёртки тонкие;
- `.gitattributes` фиксирует LF в репозитории и в контейнерах независимо от
  `core.autocrlf`, CRLF - только для `*.ps1`;
- вывод в консоль не падает на устаревших кодовых страницах Windows
  (`errors="backslashreplace"`), продюсер печатает только ASCII;
- CI гоняет тесты на Ubuntu и Windows (Python 3.10 и 3.12) и отдельно -
  `docker compose up` со сценарием проверяющего.

**Почему не только Docker.** «Запускайте всё в контейнере» снимает вопрос ОС для
сервиса, но не для продюсера и не для разработки в IDE, а именно там сломалось.
**Последствия.** Две обёртки задач нужно держать синхронными - их набор задач
одинаков и проверяется в CI вызовом `help` на Windows; содержательная логика в
обёртках не живёт.

## ADR-017. Слои: команды, ридеры, исключения и Depends

**Контекст.** Первая версия держала логику чтения и выбор ответа в ручке
(`if campaign is None: ...`), а сущности, перечисления и схемы лежали по одному
модулю на слой.
**Решение.**
- запись идёт через команду (`IngestCallHandler.handle(IngestCallCommand)`), чтение
  через ридеры (`CampaignCallsReader`, `HealthReader`);
- ридер сообщает о бизнес-ситуации исключением (`CampaignNotFoundError`,
  `ServiceNotReadyError`), инфраструктура о сбое (`StorageUnavailableError`);
  `api/errors.py` переводит их в ответы: 200 «Кампания не найдена», 503 с отчётом о
  готовности, 503 `ErrorResponse`;
- ручки получают всё через `Depends`, включая `campaign_id` и пагинацию, поэтому
  они не зависят от `app.state` и в тестах подменяются через `dependency_overrides`;
- объекты процесса собирает `Container` (composition root) в lifespan;
- датаклассы, перечисления и DTO разнесены по пакетам `models`, `enums`, `dto`,
  по одному понятию на файл;
- аннотации типов обязательны везде, включая тесты (`mypy --strict` без
  исключений, ruff `ANN`).

**Почему исключение для «не найдено», если ответ 200.** Задание требует код 200,
но для сервисного слоя это всё равно отсутствие кампании, а не успешный результат.
Исключение держит ридер честным (возвращает только найденное), а странность
контракта живёт в одном обработчике.
**Последствия.** Новый сценарий ошибки добавляется исключением и обработчиком, без
правки ручек. Схемы обоих ответов 200 и ответа 503 описаны в OpenAPI.

## ADR-018. Конфигурация через .env

`.env.example` перечисляет все настройки со значениями по умолчанию; тест сверяет
его с `Settings`, чтобы файл не устаревал. Приложение на хосте читает `.env`
(pydantic-settings). В docker compose `.env` подключается как необязательный
`env_file`, но адреса MongoDB и RabbitMQ задаются в `environment` и имеют
приоритет: внутри сети compose сервисы доступны по именам, а не по `localhost`.
